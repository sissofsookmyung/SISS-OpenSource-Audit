# Falco 커밋 분석 - 155116e

**주제:** 커널 모듈 로딩 시 신뢰할 수 없는 실행 경로 사용 방지

## 개요

Falco는 실행 중 발생하는 시스템 이벤트를 분석해 의심스러운 행위를 탐지하는 보안 도구다. 이번 분석은 Falco의 탐지 규칙이 아니라, 커널 모듈을 로딩하는 과정에서 외부 프로그램을 실행하는 방식의 보안 강화에 관한 것이다.

기존에는 `modprobe`를 실행할 때 `PATH` 환경변수에 따라 실행 파일을 선택했다. 이 커밋은 고정된 절대 경로를 사용하고 셸을 거치지 않도록 변경해, 공격자가 실행 대상을 바꿀 수 있는 위험을 줄였다.

## 변경 요약

### 기존 동작과 문제

커널 모듈 엔진에서 최초 `open_kmod()` 호출이 실패하면, Falco는 `modprobe`로 모듈 로딩을 시도한 뒤 `open_kmod()`를 다시 호출했다. `modprobe`는 커널 모듈을 로딩하는 데 사용되는 프로그램이다.

기존 호출은 다음과 같았다.

```cpp
if(system("modprobe " DRIVER_NAME " > /dev/null 2> /dev/null")) {
```

`system()`은 셸을 통해 명령을 실행한다. 여기서 `modprobe`는 절대 경로가 아니므로, 셸이 Falco 프로세스에서 상속한 `PATH`를 검색해 실행 파일을 선택한다. 따라서 실행 대상이 고정된 시스템 경로로 제한되지 않았다.

### 수정 내용

기존 호출을 새 보조 함수로 교체했다.

```diff
- if(system("modprobe " DRIVER_NAME " > /dev/null 2> /dev/null")) {
+ if(!falco_modprobe(DRIVER_NAME)) {
```

`falco_modprobe()`의 동작은 다음과 같다.

1. `/usr/sbin/modprobe`, `/sbin/modprobe` 순서로 실행 가능한 경로를 찾는다.
2. 후보가 없으면 오류를 기록하고 `false`를 반환한다.
3. `fork()`로 자식 프로세스를 만든다.
4. 자식은 표준 출력과 표준 오류를 `/dev/null`로 돌리는 처리를 시도한 뒤, `execl()`로 선택한 절대 경로의 프로그램을 직접 실행한다.
5. 부모는 `waitpid()`로 자식의 종료를 기다린다.
6. 자식이 정상 종료하고 종료 코드가 0일 때만 성공으로 처리한다.

`fork()` 또는 `waitpid()`가 실패하면 오류를 기록하고 실패를 반환한다. 자식에서 `execl()`이 실패하면 종료 코드 127로 종료한다. 보조 함수가 실패를 반환하더라도 호출부에는 오류 로그 이후 두 번째 `open_kmod()` 호출이 남아 있다.

### 공격이 성립하는 조건

커밋과 PR 설명에 따르면, 위험이 성립하려면 커널 모듈 로딩 보조 경로가 실행되고 공격자가 다음 중 하나에 영향을 줄 수 있어야 한다.

- Falco 프로세스의 `PATH` 환경변수
- 정상 `modprobe`보다 먼저 검색되는 디렉터리의 실행 파일

이 조건이 충족되면 공격자가 준비한 `modprobe`라는 이름의 프로그램이 Falco 프로세스의 권한으로 실행될 수 있다. 영향은 Falco의 실행 권한과 배포 환경에 따라 달라진다. 이 변경만으로 모든 Falco 설치에서 root 권한 탈취가 가능했다고 판단할 수는 없다.

CWE-426은 외부에서 영향을 줄 수 있는 검색 경로를 사용해 중요한 자원을 선택하는 약점이다. 이번 수정의 핵심은 실행 대상 선택을 `PATH`에 맡기지 않는다는 점이다. 코드에 사용자 입력이 문자열로 삽입되는 정황을 근거로 한 분석은 아니며, 주된 문제는 실행 파일의 검색 경로다.

### 배포 환경에 따른 영향과 남는 전제

개발자는 유지 관리되는 systemd 배포에서 `falco-kmod-inject.service`가 절대 경로로 모듈을 사전에 로딩하므로, 해당 보조 경로에 일반적으로 도달하지 않는다고 설명했다. 따라서 수동 실행·비 systemd·컨테이너 실행 등에서 실제 경로 도달 여부와 실행 환경을 살펴볼 필요가 있다. 해당 환경이라는 이유만으로 공격이 성립하는 것은 아니다.

분석상 고정된 시스템 디렉터리와 실행 파일이 적절히 보호돼 있어야 한다는 전제도 남는다. 절대 경로 지정은 실행 파일 자체의 변조나 모든 환경변수 관련 위험까지 해결한다는 의미는 아니다.

## 관련 PR 및 리뷰

[PR #3943](https://github.com/falcosecurity/falco/pull/3943)의 본문에서 개발자는 이 변경을 낮은 심각도의 보안 강화이자 심층 방어로 설명했다. 비공개 보안 신고 절차로 보고·확인됐으며, GHSA로 추적하지 않는다고 명시했다.

로컬 Git에서 확인한 반영 커밋의 순서는 다음과 같다.

| 커밋 | 역할 |
| --- | --- |
| `155116e` | `PATH` 검색 제거 및 절대 경로 기반 직접 실행 도입 |
| `954e991` | POSIX 관련 처리를 Linux 조건으로 제한하고, `waitpid()`가 `EINTR`로 중단되면 재시도하도록 보완 |
| `2656c5a` | 커널 모듈 로딩 로그도 Linux 조건문 안으로 이동 |

최초 커밋 `155116e` 자체에는 Linux 조건부 컴파일과 `EINTR` 재시도 처리가 포함돼 있지 않다. 후속 커밋에서는 플랫폼 호환성과 대기 중 인터럽트 처리를 보완했다. 리뷰어는 Linux에서만 수행하는 작업의 로그도 같은 조건 안에 있어야 한다고 제안했고, 마지막 수정에 반영됐다.

세 커밋은 로컬 이력에서 선형으로 이어진다. `2656c5a`는 마지막 후속 커밋이며, 부모가 둘 이상인 병합 커밋은 아니다. PR 전체 변경을 비교할 때는 `155116e`의 부모와 `2656c5a`를 비교한다.

## 결론 및 배운 점

이번 커밋은 Falco의 커널 모듈 로딩 보조 경로에서 외부 프로그램의 실행 대상을 선택하는 방식을 개선한 보안 강화다. 고정된 절대 경로와 직접 실행을 통해 `PATH`에 의존한 프로그램 선택을 제거했다. 직접적인 영향 범위는 런타임의 모듈 로딩이며, CI/CD 서명 절차를 변경한 패치는 아니다.

이번 분석을 통해 외부 프로그램의 이름과 전달 인자뿐 아니라, 실행 파일의 위치를 누가 결정하는지도 보안 검토 대상임을 배웠다. 또한 실패 후 실행되는 예외 처리 경로에서도 높은 권한으로 외부 프로그램이 실행될 수 있으므로, 정상 경로와 함께 살펴봐야 한다.

보안 효과를 평가할 때는 공격자가 통제할 수 있는 범위, 해당 코드에 도달하는 조건, 실제 실행 권한을 함께 확인해야 한다. 리뷰 과정에서는 보안 수정뿐 아니라 플랫폼 호환성, 인터럽트 처리, 로그의 정확성까지 보완된다는 점도 확인했다.
