## 🔍 변경 요약

### 1. 변경 배경

ModSecurity는 웹 애플리케이션 방화벽(WAF)으로, HTTP 요청과 응답을 검사하여 비정상적인 행위를 탐지하는 오픈소스 보안 소프트웨어이다.

이번 커밋에서는 `@validateByteRange`와 `@rxGlobal` 연산자가 로그에 기록하는 위치 정보(offset)의 개수를 제한하는 수정이 이루어졌다.

기존에는 두 연산자가 검사 과정에서 발견한 위치 정보를 제한 없이 로그 참조 문자열에 추가하였다.

- **`@validateByteRange`:** 허용된 바이트 범위를 벗어나는 바이트마다 위치 정보를 기록한다.
- **`@rxGlobal`:** 정규표현식에 일치하는 캡처마다 위치 정보를 기록한다.

예를 들어 40개의 바이트가 허용 범위를 벗어났다면 기존에는 40개의 위치 정보가 모두 기록되었다.

이러한 방식은 작은 입력에서는 큰 문제가 되지 않지만, `REQUEST_BODY`처럼 큰 데이터를 검사할 때 로그 참조 문자열이 과도하게 길어질 수 있다는 문제가 있었다.

PR 설명에 따르면 각 위치 정보가 최대 11자 정도를 차지할 수 있어, 로그 참조 문자열의 크기가 검사 대상 데이터의 약 10배까지 증가할 수 있었다.

특히 해당 문자열은 다음과 같은 과정에서 사용된다.

1. 트랜잭션이 유지되는 동안 `Transaction::m_rulesMessages`에 보관된다.
2. 감사 로그 생성 과정에서 다시 복사된다.
3. JSON 감사 로그에 전체 문자열이 기록된다.

기존 Error Log와 Native Audit Log는 참조 문자열을 200자로 잘라 출력했지만, 이는 전체 문자열이 생성되고 복사된 이후에 적용되는 제한이었다.

따라서 출력 길이를 제한하는 것만으로는 불필요한 메모리 사용을 방지하기 어려웠다.

### 2. 주요 코드 변경

**① 최대 로그 기록 개수 상수 추가**

변경 파일: `src/operators/operator.h`

```cpp
static constexpr size_t MAX_LOGGED_OFFSETS = 20;
```

한 번의 연산자 평가에서 로그 참조 문자열에 추가할 위치 정보의 최대 개수를 20개로 설정하였다.

이를 통해 입력 데이터의 크기와 관계없이 해당 연산자가 기록하는 offset 개수에 상한을 두었다.

**② `@rxGlobal` 연산자 수정**

변경 전:

```cpp
for (const auto & capture : captures) {
    logoffset(ruleMessage, capture.m_offset, capture.m_length);
}
```

변경 후:

```cpp
for (size_t i = 0;
     i < captures.size() && i < MAX_LOGGED_OFFSETS;
     i++) {
    logoffset(ruleMessage, captures[i].m_offset, captures[i].m_length);
}
```

기존에는 정규표현식에 일치하는 모든 캡처의 위치 정보를 기록하였다.

변경 후에는 `MAX_LOGGED_OFFSETS` 조건을 추가하여 최초 20개의 캡처 위치만 기록하도록 수정하였다.

단, 실제 정규표현식 검사와 캡처 저장은 기존과 동일하게 수행된다.

**③ `@validateByteRange` 연산자 수정**

기존에는 허용 범위를 벗어난 모든 바이트의 위치 정보를 기록하였다.

변경 후에는 최초 20개의 위치 정보만 기록하도록 수정하였다.

다만 20개를 초과하는 바이트도 계속 검사하고 범위 초과 개수도 계산하므로, 입력값 검증 결과에는 영향을 주지 않는다.

### 3. 변경 전후 비교

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 위치 정보 기록 | 모든 일치 위치 기록 | 최대 20개 기록 |
| 로그 크기 | 입력에 따라 과도하게 증가 가능 | 위치 정보 기록량 제한 |

## 🔐 보안 관점 분석

### 1. 보안적 의미

이번 수정은 로그 참조 문자열이 입력 데이터의 크기에 따라 과도하게 증가하는 문제를 개선한 것이다.

웹 애플리케이션 방화벽은 외부에서 전달되는 HTTP 요청을 지속적으로 검사한다. 따라서 공격자가 비정상적으로 크거나 반복적인 데이터를 전송할 경우, 검사 과정에서 불필요한 자원이 소비되지 않도록 관리하는 것이 중요하다.

기존 방식에서는 요청 데이터에 일치 항목이 많을수록 로그 참조 문자열도 함께 증가하였다.

이는 메모리 사용량 증가와 로그 생성 과정의 처리 부담으로 이어질 가능성이 있었다.

이번 수정은 위치 정보 기록을 최대 20개로 제한하여 이러한 부담을 줄이도록 설계되었다.

특히 **실제 탐지 결과를 변경하지 않으면서 로그 기록 방식만 수정했다는 점**이 중요하다.

### 2. 보안 분석표

| 항목 | 이전 버전 | 변경 버전 | 보안적 의미 |
|---|---|---|---|
| 로그 기록 개수 | 제한 없음 | 최대 20개 | 과도한 로그 생성 억제 |
| 메모리 사용 | 입력 크기에 따라 증가 | 로그 참조 크기 증가 제한 | 자원 사용 부담 완화 |
| 입력값 검증 | 전체 입력 검사 | 전체 입력 검사 유지 | 탐지 기능 유지 |
| 감사 로그 | 긴 참조 문자열 기록 | 기록량 제한 | 로그 처리 효율 개선 |
| 회귀 테스트 | 관련 테스트 부재 | 2개 사례 추가 | 동일 문제 재발 방지 |

### 3. 보안 취약점과의 관계

이번 수정은 입력 데이터에 따라 로그 참조 문자열이 과도하게 커지는 문제를 해결한다는 점에서 보안 안정성과 관련이 있다.

다만 해당 문제가 실제 서비스 거부(DoS) 공격으로 악용되었는지에 대한 증거는 확인하지 못하였다.

따라서 이번 커밋을 특정 CVE 취약점에 대한 패치라고 단정하기보다는 **잠재적인 자원 소모 문제를 완화하는 안정성 개선**으로 분류하는 것이 적절하다.

## 💬 결론

### 1. 업데이트 성격

**안정성 개선 및 잠재적인 자원 소모 문제 완화**

이번 커밋은 ModSecurity의 `@validateByteRange`와 `@rxGlobal` 연산자가 로그에 기록하는 위치 정보를 최대 20개로 제한한 수정이다.

기존에는 입력 데이터에 따라 로그 참조 문자열이 과도하게 증가할 수 있었으며, 해당 문자열이 트랜잭션 동안 메모리에 보관되고 감사 로그 생성 과정에서 복사된다는 문제가 있었다.

개발자는 로그 기록 개수에 상한을 설정하여 불필요한 메모리 사용과 로그 처리 부담을 줄이도록 수정하였다.

### 2. CI/CD 신뢰성 영향

**긍정적 영향 있음**

특히 패치 적용 전에는 실패하고 적용 후에는 통과하는 테스트 사례가 추가되어 수정 의도를 검증할 수 있었다.

이번 분석을 통해 보안 소프트웨어에서는 공격 탐지 기능뿐 아니라 탐지 과정에서 생성되는 로그와 메모리 사용량도 중요하다는 점을 확인하였다.

처음에는 단순히 로그에 기록되는 개수를 줄이는 수정이라고 생각했지만, PR을 확인하면서 해당 문자열이 메모리에 보관되고 감사 로그 생성 과정에서 복사된다는 점을 알게 되었다.

특히 기존에는 로그 출력 길이가 제한되어 있어도 내부적으로는 전체 문자열이 생성된다는 점이 인상적이었다. 화면에 출력되는 로그의 길이와 실제 메모리에서 처리되는 데이터의 크기는 다를 수 있다는 것을 이해할 수 있었다.

또한 이번 수정은 로그 기록량을 줄이면서도 실제 탐지 결과는 유지하도록 설계되었다. 이를 통해 보안 기능의 정확성을 유지하면서 시스템의 자원 사용을 개선하는 방법을 살펴볼 수 있었다.

이번 커밋은 직접적인 CVE 패치로 확인되지는 않았지만, 보안 도구의 안정성과 자원 관리 측면에서 의미 있는 개선 사례라고 판단하였다.
